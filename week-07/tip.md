# Tips for this week

This week I focused on the practical side of preparing the project so that it could be understood, reviewed, and potentially deployed by someone other than the development team. At this stage, it became increasingly clear that producing a working application was only part of the requirement. The project also needed to be documented properly and structured in a way that made deployment more realistic, especially as the brief expects the client to be able, in theory, to walk away with a working application and supporting materials.


A key issue I considered this week was deployment. As development progressed, it became obvious that there were several technical details that could create problems when moving from local development to a deployed version of the application. These included areas such as environment configuration, dependency management, database setup, and framework-related issues that could affect whether the application built and ran correctly outside our own machines. Reflecting on this made me realise that deployment is not just a final step at the end of the project, but something that needs to be considered throughout development if the application is going to be reliable and presentable.

I also thought about the documentation the project would need in order to support both assessment and client handover. This included the need for clear setup instructions, a basic explanation of how to run the application, and guidance on how different features should be used. I saw documentation as especially important in our project because it helps bridge the gap between the technical work completed by the team and the practical understanding needed by lecturers, teammates, or the client. Without clear documentation, even strong technical work can be much harder to evaluate or reuse.


My contribution this week was therefore focused on recognising and helping address the gap between development and delivery. Rather than only concentrating on new features, I spent time thinking about what would be required for the application to be more complete as a professional product. This included considering what technical setup details would need to be explained, what common issues would need to be documented, and how we could make the project easier to review and demonstrate.
Overall, this week helped me understand that software quality is not only measured by the features inside the application, but also by how clearly it can be deployed, explained, and maintained. Looking back, this was an important stage because it pushed my thinking beyond coding alone and toward the wider expectations of delivering a usable and professional piece of software.
